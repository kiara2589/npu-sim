# 🧠 Mini NPU Simulator (Pre-course Mission 3)

본 프로젝트는 AI 전용 반도체 NPU(Neural Processing Unit)의 핵심 연산인 **MAC(Multiply-Accumulate, 곱셈-누적) 연산 원리**를 흉내 내는 Python 기반의 콘솔 시뮬레이터 애플리케이션입니다. 

순수 파이썬 이중 반복문으로 $3\times3$부터 $25\times25$까지의 패턴 유사도를 판별하고, 부동소수점 연산 오차 처리(Epsilon 정책), 패턴 크기 증가에 따른 연산 시간 복잡도($O(N^2)$), 대규모 데이터($N \ge 1000$) 최적화 방안 및 CPU vs NPU 하드웨어 구조적 병목을 심층 분석합니다.

## 💻 2. 주요 핵심 소스 코드 (Key Source Code)

### 2.1. MAC(Multiply-Accumulate) 연산 (`src/mac.py`)
> 외부 라이브러리(NumPy 등) 없이 이중 반복문으로 위치별 곱셈과 누적 합산을 직접 계산합니다.

```python
def mac(pattern, filt):
    """
    순수 이중 반복문 기반 2차원 MAC 연산.
    패턴과 필터의 동일 위치 요소를 곱한 뒤 누적 합계를 반환합니다.
    """
    total = 0.0
    n = len(pattern)
    for i in range(n):
        for j in range(n):
            total += pattern[i][j] * filt[i][j]
    return total
```

### 2.2. 라벨 정규화 및 허용오차(Epsilon) 판정 (`src/judge.py`)
> 다양한 유형의 라벨을 표준화하고, 부동소수점 연산 오차로 인한 판정 오류를 Epsilon 정책으로 방지합니다.

```python
EPSILON = 1e-9

def normalize_label(raw):
    """라벨 문자열을 표준 라벨('Cross', 'X')로 정규화"""
    if raw is None:
        return None
    key = str(raw).strip().lower()
    if key in ("+", "cross", "plus"):
        return "Cross"
    if key in ("x", "ex"):
        return "X"
    return None

def judge(score_a, score_b, label_a="Cross", label_b="X"):
    """
    |a - b| < EPSILON인 경우 부동소수점 누적 오차로 간주하여
    동점(UNDECIDED)으로 판정하고, 그렇지 않을 경우 우세한 필터를 반환합니다.
    """
    if abs(score_a - score_b) < EPSILON:
        return "UNDECIDED"
    return label_a if score_a > score_b else label_b
```

### 2.3. 연산 성능 측정 모듈 (`src/perf.py`)
> 입출력(I/O) 시간을 제외하고 순수 `mac()` 함수 실행 구간만 10회 반복 측정하여 평균 ms를 구합니다.

```python
import time
from src.mac import mac

REPEAT_COUNT = 10

def measure_mac_ms(pattern, filt, repeat=REPEAT_COUNT):
    """perf_counter 기반 MAC 연산 평균 실행 시간(ms) 산출"""
    start_time = time.perf_counter()
    for _ in range(repeat):
        mac(pattern, filt)
    end_time = time.perf_counter()
    
    elapsed_total_sec = end_time - start_time
    avg_ms = (elapsed_total_sec / repeat) * 1000.0
    return avg_ms
```

### 6.2. 실패 케이스 원인 심층 분석

본 시뮬레이터에서 발생한 3건의 `FAIL` 케이스(`size_5_1`, `size_13_2`, `size_25_1`)는 프로그램 로직의 결함이나 데이터 스키마의 오류가 아닌, **수치 비교(부동소수점 연산 오차 및 의도된 동점 정책)**에 의해 발생한 정상적인 검증 결과입니다.

1. **데이터 설계 특성 분석:**
   * 해당 케이스들의 Cross 필터 점수와 X 필터 점수를 계산하면 $0.9$, $7.5$, $4.9$로 두 필터의 점수가 정확히 동일합니다. 이는 정밀한 부동소수점 오차 검증을 위해 의도적으로 구성된 데이터셋입니다.
2. **단순 동등 비교(`==`) 사용 시 문제점:**
   * 컴퓨터는 실수를 2진수로 변환해 저장하므로 부동소수점 오차(예: `0.1 + 0.2 = 0.30000000000000004`)가 누적됩니다.
   * 단순 `==` 비교를 수행할 경우 무의미한 $10^{-16}$ 미세 차이로 인해 한쪽 라벨이 임의 선택되어 판정되는 '로직 오류' 현상이 발생합니다.
3. **허용오차(Epsilon) 비교 정책 적용 효과:**
   * 본 시뮬레이터는 `abs(score_a - score_b) < 1e-9` 조건의 Epsilon 정책을 적용하여, 미세 오차 범위 내 점수를 안전하게 `UNDECIDED`(판정 불가)로 분류했습니다.
   * 동점 판정을 받은 케이스들이 단일 expected 라벨(`X` 또는 `Cross`)과 일치하지 않아 의도된 대로 `FAIL` 처리되었습니다.

### 6.3. 시간 복잡도 분석 ($O(N^2)$)

#### 1) 연산 횟수와 이론적 복잡도
$N \times N$ 크기의 패턴과 필터에 대한 MAC 연산은 행 $N$개와 열 $N$개를 모두 순회하는 이중 반복문으로 구현됩니다. 따라서 총 곱셈 및 덧셈 연산 횟수는 정확히 $N^2$번이며, 시간 복잡도는 **$O(N^2)$**을 가집니다.

#### 2) 크기별 연산 성능 측정 결과 (10회 평균)

| 크기 ($N \times N$) | 연산 횟수 ($N^2$) | 이론적 연산량 증가율 | 실측 평균 연산 시간 (ms) |
| :---: | :---: | :---: | :---: |
| **$3 \times 3$** | 9 | 1.00배 (기준) | 약 0.0022 ms |
| **$5 \times 5$** | 25 | 2.78배 | 약 0.0051 ms |
| **$13 \times 13$** | 169 | 18.78배 | 약 0.0210 ms |
| **$25 \times 25$** | 625 | 69.44배 | 약 0.0680 ms |

*(※ 실측 연산 시간은 실행 컴퓨터 사양 및 파이썬 런타임 환경에 따라 약간의 편차가 발생할 수 있습니다.)*

#### 3) 실측값과 이론값 연결 및 고정 비용(Fixed Cost) 설명
* $3 \times 3$ 대비 $25 \times 25$의 이론적 연산 횟수는 $9$회에서 $625$회로 **69.44배** 증가합니다.
* 실측된 시간도 크기가 증가함에 따라 곡선을 그리며 $O(N^2)$ 추세를 그대로 반영하여 증가합니다.
* 정확히 $69.44$배에 완벽히 비례하지 않는 이유는 **파이썬 런타임의 고정 비용(Fixed Cost)** 때문입니다:
  1. `mac()` 함수 진입 및 반환 오버헤드
  2. 반복문 제어 변수(`range`) 생성 및 메모리 인덱싱 비용
  3. 타이머 측정 함수(`time.perf_counter()`) 자체의 실행 비용
* 배열 크기 $N$이 커질수록 이러한 고정 비용이 차지하는 비중이 감소하고, 순수 $N^2$ 연산 시간이 전체 실행 시간을 지배하게 됨을 확인할 수 있습니다.

### 6.4. 대규모 데이터($N \ge 1000$) 처리 시 병목 및 최적화 방안

패턴의 크기가 $1000 \times 1000$ 이상으로 커질 경우, 단일 MAC 연산 횟수는 최소 **1,000,000회($10^6$번)**로 기하급수적으로 폭증합니다. 파이썬 환경에서 이러한 대규모 데이터를 처리할 때 발생하는 주요 병목 원인과 최적화 방안은 다음과 같습니다.

#### 1) 시간 및 메모리 예상 병목 문제
* **메모리 파편화 및 오버헤드:** 파이썬의 2차원 리스트(`list[list]`)는 각 요소를 독립된 포인터 객체로 관리합니다. $1000 \times 1000$ 배열 생성 시 불필요한 객체 헤더 메모리 오버헤드가 발생하며, 힙(Heap) 영역 메모리 파편화로 인해 CPU L1/L2 캐시 미스(Cache Miss) 확률이 치솟습니다.
* **시간 복잡도 제약 ($O(N^2)$):** 순수 이중 `for`문 순회 시 인터프리터 바이트코드 해석 오버헤드가 백만 번 누적되어 실행 시간이 밀리초(ms) 단위에서 수 초(초) 단위로 급증합니다.

#### 2) 우선 최적화 대상 (메모리 및 알고리즘)

| 구분 | 병목 원인 | 우선 최적화 방안 (Optimization Strategy) |
| :--- | :--- | :--- |
| **메모리 최적화** | 2차원 포인터 배열의 캐시 미스 | **1차원 평탄화(Flattened 1D Array):** $N \times N$ 배열을 연속된 1차원 메모리 블록으로 변환하여 데이터 국소성(Data Locality) 확보 및 캐시 적중률(Cache Hit Ratio) 극대화 |
| **메모리 최적화** | 파이썬 객체 포인터 오버헤드 | **연속 메모리 뷰(Memoryview / Ctype):** 파이썬 고유 객체 오버헤드를 없애고 C-스타일 연속 바이트 버퍼 메모리 직접 참조 사용 |
| **알고리즘 최적화** | 단일 스레드 순차 이중 루프 | **블록 타일링(Block Tiling):** CPU L1/L2 캐시 크기(예: 32KB/512KB)에 맞춰 연산 행렬을 작은 Tile 단위로 분할하여 캐시 적중률 향상 |
| **실행/구현 최적화** | 바이트코드 해석 연산 지연 | **SIMD / 벡터화 연산 도입:** CPU의 AVX-512 등의 SIMD 명령어 세트 활용 또는 C-Extension 백엔드 연산(NumPy Native C Engine)으로 전환 |

### 6.5. CPU vs NPU 하드웨어 구조적 병목 심층 비교

대규모 MAC 연산 시 CPU와 NPU가 보이는 성능 차이와 하드웨어적 병목 포인트를 비교 분석합니다.

#### 1) CPU vs NPU 구조적 특성 비교

| 구분 | CPU (Central Processing Unit) | NPU (Neural Processing Unit) |
| :--- | :--- | :--- |
| **코어 구조** | 4~16개 고성능 코어 (복잡한 제어 장치, 대용량 캐시) | 수천 개의 단순 MAC 전용 연산 회로 (Systolic Array 등) |
| **연산 방식** | 복잡한 명령어의 **직렬(Sequential) 처리** | 대규모 곱셈-누적(MAC)의 **극단적 병렬(Parallel) 처리** |
| **메모리 구조** | Von Neumann 구조 (DRAM $\leftrightarrow$ Cache $\leftrightarrow$ ALU) | Processing-In-Memory(PIM) 또는 On-Chip SRAM 가속 |
| **주요 역할** | 범용 OS 제어, 복잡한 분기문 및 알로케이션 처리 | 딥러닝 추론/학습 시 반복되는 대규모 텐서/MAC 연산 가속 |

#### 2) 하드웨어 관점 병목 포인트 (Memory Bandwidth & Parallelism)

* **CPU 관점의 병목 포인트 (폰 노이만 병목):**
  * **메모리 대역폭 한계(Memory Bandwidth Bottleneck):** CPU는 ALU의 연산 속도보다 주메모리(DRAM)에서 데이터를 읽고 쓰는 데이터 전송 속도가 훨씬 느립니다. $1000 \times 1000$ MAC 연산 시 ALU는 계산 준비가 되어도 DRAM 전송 지연(Latency) 때문에 대기(Stall) 상태에 빠집니다.
  * **직렬 루프 제어 병목:** 코어 수가 적어 $N^2$ 연산을 순차적으로 수행해야 하므로, 병렬로 동시 계산을 처리하지 못하는 한계가 존재합니다.
* **NPU 관점의 병목 포인트 (SRAM 용량 & 데이터 틸링):**
  * **On-Chip SRAM 용량 제한:** NPU는 MAC 연산 회로 격자(Systolic Array)에 필터와 패턴 데이터를 올려두고 동시 연산합니다. 그러나 패턴/필터 크기가 NPU의 내부 SRAM 버퍼 용량을 초과하면, 데이터를 나누어 입력하는 **데이터 틸링(Data Tiling) 및 DMA 전송 병목**이 발생합니다.
  * **Off-Chip 메모리 입출력 병목:** NPU 내부 연산 속도는 매우 빠르지만, 외부 DRAM에서 On-Chip 버퍼로 텐서 데이터를 로드할 때 메모리 인터페이스 대역폭 한계에 직면하게 됩니다.
